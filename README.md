# Medication API

A production-ready REST API in Go to manage medication records (create, read, list, update, delete).

The domain is small on purpose, so the project focuses on the foundations that matter in production: a clean architecture, strict input handling, consistent errors, safe concurrency, real persistence with migrations, observability, graceful shutdown, tests at every level, and a reproducible build and CI pipeline.

```
POST   /v1/medications         create
GET    /v1/medications         list (cursor pagination, filters)
GET    /v1/medications/{id}    get
PUT    /v1/medications/{id}    replace (optional If-Match)
DELETE /v1/medications/{id}    delete
GET    /healthz  /readyz       liveness / readiness probes
```

The full contract is in [`api/openapi.yaml`](api/openapi.yaml) (OpenAPI 3.1). Ready-to-run examples are in [`requests.http`](requests.http).

## Quick start

Requirements: Go 1.27+, and Docker for the full stack.

```bash
# 1. Fastest: run with in-memory storage (no database needed)
make run
curl -s -X POST localhost:8080/v1/medications \
  -H 'Content-Type: application/json' \
  -d '{"name":"Paracetamol","dosage":"500 mg","form":"tablet"}'

# 2. Full stack: API + PostgreSQL + Grafana (traces and metrics)
make up        # http://localhost:8080 and Grafana at http://localhost:3000 (GRAFANA_PORT=3001 make up if 3000 is taken)
make down
```

| Command | What it does |
|---|---|
| `make test` | Unit and HTTP tests with the race detector (integration tests are skipped) |
| `make test-integration` | Starts PostgreSQL with Docker and runs **all** tests, including integration tests |
| `make cover` | Coverage per function |
| `make lint` | golangci-lint (config in `.golangci.yml`) |
| `make fuzz` | Fuzzes the domain validation for 30 s |
| `make vuln` | govulncheck: known vulnerabilities in dependencies |
| `make docker-build` | Builds the container image |
| `make help` | Lists every command |

## The medication resource

```json
{
  "id": "0199d2a1-7c4e-7b2a-9f10-3c5d8e1a2b4c",
  "name": "Paracetamol",
  "dosage": "500 mg",
  "form": "tablet",
  "version": 1,
  "created_at": "2026-10-12T15:04:05.123456Z",
  "updated_at": "2026-10-12T15:04:05.123456Z"
}
```

| Field | Rules |
|---|---|
| `name` | required, 1–200 characters, surrounding spaces trimmed, no control characters |
| `dosage` | required, 1–100 characters (free text, e.g. `500 mg`, `120 mg/5 ml`), no control characters |
| `form` | one of `tablet`, `capsule`, `liquid`, `injection`, `cream`, `inhaler` (case-insensitive input) |
| `id` | UUIDv7, generated by the server |
| `version` | starts at 1, +1 on every update; also sent as the `ETag` header |

Business rule: the same medication (name + dosage + form, ignoring case) cannot be registered twice → `409 Conflict`.

### Errors

Every error uses [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457) (`application/problem+json`):

```json
{
  "type": "about:blank",
  "title": "Unprocessable Entity",
  "status": 422,
  "detail": "the medication is not valid",
  "instance": "/v1/medications",
  "request_id": "5f0c6c2e-...",
  "errors": [
    { "field": "name", "message": "is required" },
    { "field": "form", "message": "must be one of: tablet, capsule, liquid, injection, cream, inhaler" }
  ]
}
```

| Status | When |
|---|---|
| 400 | Malformed JSON, unknown field, invalid UUID, invalid query parameter or `If-Match` |
| 404 | The medication (or the route) does not exist |
| 405 | The route exists but not with that method (`Allow` header lists the valid ones) |
| 409 | Duplicate medication, or a concurrent update without `If-Match` |
| 412 | `If-Match` does not match the current version |
| 413 / 415 | Body larger than 1 MiB / `Content-Type` is not JSON |
| 422 | Well-formed body that breaks validation rules (all invalid fields listed) |
| 500 | Unexpected error: logged with details, the client only gets a generic message |
| 503 | The request exceeded `HTTP_REQUEST_TIMEOUT` (e.g. the database is too slow) |

`If-Match` is evaluated before the body is validated, as RFC 9110 requires: a stale ETag gets `412` even if the body is also invalid.

### Concurrency: ETag and If-Match

Two clients can read the same medication and both send an update; without protection the second silently overwrites the first ("lost update"). The API uses **optimistic concurrency control**:

1. `GET` returns `ETag: "3"` (the version).
2. The client sends `PUT` with `If-Match: "3"`.
3. If someone else updated it first, the version is now 4 and the API answers `412 Precondition Failed`. The client re-reads and retries.

In PostgreSQL the check and the write are one atomic statement (`UPDATE ... WHERE id = $1 AND version = $2`), so there is no race window. Even without `If-Match`, a concurrent modification between the read and the write is rejected with `409` rather than lost.

### Pagination

`GET /v1/medications?limit=20` returns `{"data": [...], "next_cursor": "..."}`. Pass `cursor=<next_cursor>` to get the next page; `next_cursor` is absent on the last page. Filters: `form=tablet`, `name=para` (contains, case-insensitive).

This is **keyset pagination**: the cursor encodes the last ID of the page, and the query asks for `id > cursor ORDER BY id LIMIT n`. Unlike `OFFSET`, it costs the same on page 1 and page 10,000 (the primary key index jumps straight to the cursor), and deleting or inserting rows on earlier pages does not shift later pages, so rows are not repeated. Cursors are opaque (base64url) so the strategy can change without breaking clients.

Results are ordered by ID. IDs are UUIDv7, so this is creation order, with one caveat: an ID is generated just before its INSERT commits, so two concurrent inserts can commit in the opposite order of their IDs (and clocks differ slightly between replicas). A client that is paginating at that exact moment may miss a row that commits "behind" its cursor. That is acceptable for browsing a catalog; a strict change feed would use a commit-ordered sequence or an outbox table instead.

## Architecture

Hexagonal architecture (ports and adapters), organized by feature:

```
cmd/medication-api/        main: configuration, wiring (manual DI), graceful shutdown
internal/
  medication/              DOMAIN: entity, validation, errors, service, Repository port
    medicationtest/        contract test suite every Repository must pass
  adapter/
    httpapi/               HTTP adapter: routes, JSON, problem details, middleware, probes
    memory/                Repository in memory (local runs, HTTP tests)
    postgres/              Repository on PostgreSQL (pgx), migrations runner
  config/                  environment variables → typed Config, validated at startup
  telemetry/               slog logger with trace IDs, OpenTelemetry setup
migrations/                SQL migrations, embedded into the binary
api/openapi.yaml           API contract
```

```
   httpapi ──► medication ◄── postgres
               (domain)   ◄── memory
   main wires everything together
```

**The rule:** dependencies point towards the domain. `internal/medication` imports no HTTP, JSON or SQL package; adapters import the domain, never the other way around. The `Repository` interface is declared in the domain (the consumer) and implemented by the adapters, following the Go idiom *accept interfaces, return structs*. Consequences:

- Business rules are tested without a database or a server (milliseconds).
- Storage can change (in-memory ↔ PostgreSQL, or another database) without touching business rules.
- Every concern has an obvious home.

`internal/` is enforced by the Go compiler: no code outside this module can import these packages.

### Request flow

```
HTTP request
 └─ tracing (OpenTelemetry span, continues the caller's trace)
     └─ requestID (X-Request-ID, propagated or generated)
         └─ logRequests (one structured access log line per request)
             └─ recoverPanics (a panic becomes a 500, not a dropped connection)
                 └─ timeout (deadline on the request context; slow queries are canceled)
                     └─ ServeMux → handler: decode + validate input
                         └─ medication.Service: business rules, clock, ID generation
                             └─ Repository (PostgreSQL or memory)
 ◄─ errors mapped to status codes in one place (writeError)
```

## Design decisions and trade-offs

| Decision | Why | Trade-off / alternative |
|---|---|---|
| Standard library `net/http` router | Since Go 1.22 `ServeMux` supports methods and path wildcards (`GET /v1/medications/{id}`). Zero dependencies. | chi/echo add route groups and helpers; not needed for five routes. |
| Hexagonal, package by feature | Testable domain, swappable adapters, clear boundaries. | More files than a single package; worth it once there is real persistence. |
| UUIDv7 IDs (Go 1.27 standard library `uuid`) | Generated by the app before inserting, not guessable, time-ordered: new rows land at the end of the B-tree index (like an auto-increment) and enable keyset pagination by ID. | 16 bytes vs 8 for a bigint. |
| Domain functions are pure | `medication.New(id, attrs, now)` receives the ID and time; the service owns the clock and ID generator (injectable with functional options). Deterministic tests. | One extra parameter. |
| Hand-written validation in the domain | Rules live in one place, collect **all** errors, count characters (runes), not bytes, and reject invalid UTF-8. | A validation library would add struct tags and reflection to the domain. |
| Errors: sentinels + typed `ValidationError`, wrapped with `%w` | Callers use `errors.Is/As`; context is added at each layer without losing the cause. Unexpected errors are logged **once**, at the edge. | — |
| RFC 9457 Problem Details | A standard error format clients can handle generically. | — |
| Strict JSON decoding | Unknown fields, trailing data, wrong `Content-Type` and bodies > 1 MiB are rejected instead of silently ignored. | Clients cannot send extra fields (intended). Like any `encoding/json` decoder, field names are matched case-insensitively (`"NAME"` works). |
| PostgreSQL + pgx v5 (hand-written SQL) | pgx is the most complete native driver; SQL is short and visible. Unique index enforces the duplicate rule under concurrency. LIKE wildcards in the search are escaped. | sqlc would generate type-safe code from SQL; worth it with more queries. |
| Migrations with goose, embedded with `go:embed` | Single binary; versioned SQL; a PostgreSQL advisory lock makes concurrent startups safe (only one replica migrates). | Running migrations on startup is convenient; large teams often run them as a separate deploy step (`DB_MIGRATE=false`). |
| Repository contract tests | One suite (`medicationtest.RunRepositoryContract`) runs against memory **and** PostgreSQL, guaranteeing identical behavior. | — |
| Integration tests via `TEST_DATABASE_URL` | Real PostgreSQL, each test in its own schema (parallel, isolated). Skipped when the variable is unset, so `go test ./...` works anywhere. CI provides a PostgreSQL service. | testcontainers-go would start the database from the test itself, at the cost of a heavier dependency tree. |
| In-memory repository when `DATABASE_URL` is empty | `make run` works with zero setup. A warning is logged. | Must never be used in production: the deployment always sets `DATABASE_URL`. |
| OpenTelemetry (OTLP/HTTP) | Vendor-neutral traces and metrics; HTTP and SQL spans; logs carry `trace_id`/`span_id`. Disabled (no-op) unless `OTEL_EXPORTER_OTLP_ENDPOINT` is set. | — |
| Graceful shutdown | On SIGTERM: `/readyz` → 503, optional drain delay, then `http.Server.Shutdown` lets in-flight requests finish (connections are force-closed after `SHUTDOWN_TIMEOUT`). Telemetry is flushed. Compose gives the container a 30 s stop grace period. | — |
| Timeouts everywhere | Server timeouts (`ReadHeaderTimeout`...) protect against slow clients (Slowloris); a per-request context deadline cancels slow database queries and answers 503, so stuck requests cannot pile up. | — |
| Keyset pagination by UUIDv7 | Constant cost per page, stable pages, no extra column. | Ordering is creation order only approximately under concurrent inserts (see Pagination). |
| Distroless, non-root, multi-arch image | No shell or package manager; small attack surface; runs on amd64 and arm64 (Graviton, Apple Silicon). | Debugging inside the container needs an ephemeral debug container. |

## Configuration

All settings are environment variables ([twelve-factor](https://12factor.net/config)). Invalid values stop the service at startup.

| Variable | Default | Description |
|---|---|---|
| `HTTP_ADDR` | `:8080` | Listen address |
| `DATABASE_URL` | *(empty → in-memory)* | PostgreSQL URL, e.g. `postgres://user:pass@host:5432/db?sslmode=require` (must be a `postgres://` URL) |
| `DB_MAX_CONNS` | `10` | Connection pool size |
| `DB_MIGRATE` | `true` | Apply pending migrations on startup |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error` |
| `LOG_FORMAT` | `json` | `json` or `text` |
| `APP_ENV` | `development` | Environment name in logs and traces |
| `HTTP_READ_HEADER_TIMEOUT` / `HTTP_READ_TIMEOUT` / `HTTP_WRITE_TIMEOUT` / `HTTP_IDLE_TIMEOUT` | `5s` / `10s` / `15s` / `60s` | Server timeouts |
| `HTTP_REQUEST_TIMEOUT` | `10s` | Deadline of each request (keep it below `HTTP_WRITE_TIMEOUT`) |
| `SHUTDOWN_TIMEOUT` | `20s` | Max time for in-flight requests after SIGTERM |
| `SHUTDOWN_DRAIN_DELAY` | `0s` | Time to keep serving while `/readyz` is 503 (use ~5s on Kubernetes) |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | *(empty → telemetry off)* | OTLP/HTTP endpoint, e.g. `http://otel-collector:4318`. Other standard `OTEL_*` variables are honored. |

The configuration is logged at startup; for the database only the scheme, host and database name are logged, never credentials.

## Observability

- **Logs:** structured JSON (`log/slog`), one access log line per request with method, route, status, duration and request ID. When a trace is active, every line includes `trace_id` and `span_id`. Probes are logged at debug level.
- **Traces:** one span per request, named after the route (`GET /v1/medications/{id}`), with child spans for every SQL query. Incoming W3C `traceparent` headers are honored (distributed tracing).
- **Metrics:** standard HTTP server metrics (request duration, sizes) and connection pool statistics.
- **Probes:** `/healthz` (liveness, no dependencies) and `/readyz` (readiness: database reachable and not shutting down).

With `make up`, open Grafana at http://localhost:3000 → Explore → Tempo to see traces, or Prometheus for metrics. If something else already uses port 3000, pick another host port with `GRAFANA_PORT=3001 make up`.

## Testing

| Level | Where | What |
|---|---|---|
| Domain unit tests | `internal/medication/*_test.go` | Validation, normalization, update rules; table-driven; service tested with a hand-written fake repository |
| Fuzz test | `internal/medication/fuzz_test.go` | Random input never panics and accepted values always satisfy the invariants |
| Repository contract | `internal/medication/medicationtest` | Same suite for memory and PostgreSQL |
| HTTP tests | `internal/adapter/httpapi/*_test.go` | Real router + middleware + service through `httptest`: status codes, problem details, ETags, pagination, limits, panics, tracing |
| Integration | `internal/adapter/postgres/*_test.go` | Real PostgreSQL, isolated schema per test |

All tests run with `-race`. The tests use only the standard library (no assertion framework), following the Go style guide.

## What I would add next (TODO)

The assignment asks to prioritize the foundation; these are the next steps for a real deployment:

- **Authentication and authorization** (e.g. OAuth2/JWT validated by middleware, scopes per operation). Today the API is open.
- **Rate limiting** per client (`golang.org/x/time/rate`, or at the API gateway).
- **`Idempotency-Key` on `POST`**, so client retries after a timeout cannot create duplicates.
- **`PATCH`** with JSON Merge Patch (RFC 7396) for partial updates.
- **`If-None-Match` / `304 Not Modified`** on `GET` to save bandwidth.
- **Soft delete and an audit trail** (who changed what, when), usually required for medical data.
- **Structured dosage** (amount + unit) if clients need to search or compute with it.
- **Search at scale**: a `pg_trgm` index for the `name` filter.
- Deployment manifests (Kubernetes/ECS), alerts and dashboards as code.
